# Pi Session Daemon

## Purpose

This module is the Pi-owned session-daemon foundation. A detached local daemon process creates an `AgentSessionRuntime` with the Pi SDK, tracks it in a registry keyed by Pi session identity and cwd, keeps it behind a private local socket, and maps a small event subset to the PiChamber IPC contract. Browsers never connect to it. Directory inputs must be absolute except for the exact `~` global-session sentinel, which the daemon expands to the server user's home directory before validation. Other relative paths remain invalid.

## Entrypoints

- `../extension-protocol.js` owns the bounded form descriptor and response validation shared by the private daemon bridge and public route projection, so both sides of the IPC seam accept the same field contract.
- Turn ownership: an assistant message belongs to the latest user prompt or displayed custom message (`pi.sendMessage` with `display: true`) before it, live (`assistant.message.start.parentId`, set from the last user start or the `extension.message` id) and in the transcript projection (`parentId` on assistant entries after a `custom_message`). Custom entries (`appendEntry`) and context-only custom messages (`display: false`) never own a turn. `agent_settled` resets the live owner.
- `extension-bridge.js` owns extension UI bindings, pending dialog lifecycle, normalized status/widget/panel/app state, snapshot projection, and extension event publication. `session-daemon.js` supplies runtime lookup, publication, redaction, and directory dependencies through its narrow factory interface.
- `session-daemon.js`
  - `createPiSessionRuntime({ cwd, agentDir })` creates a persistent Pi runtime using the selected server-side cwd and Pi agent directory. It uses Pi's normal settings, credentials, models, sessions, skills, prompts, context discovery, and native extensions. Every runtime creation binds extensions through `session.bindExtensions()` in rpc-like mode with a daemon-owned UI bridge, so pi extensions load exactly as they do under the Pi CLI's RPC mode. Sessions created outside PiChamber (Pi CLI or any other writer of the cwd-scoped JSONL directory) are the same records: `sessions.list`/`open` hydrate from `getEntries()`, then overlay the live `session.messages` / `state.streamingMessage` turn while `isStreaming` is true, including an unpersisted user prompt that has not flushed to JSONL yet. A later prompt must overlay live turns onto that log rather than replace it. An unmatched `toolCall` projects as `running` only while `isStreaming` is authoritative; the same unmatched call in an idle persisted turn projects as a timestamped interruption error instead of malformed `completed` state. `getSession` also reports `isStreaming` and `lifecycle` so a restarted UI can restore the working/tooling state without waiting for the next token.
  - Extension bridging: blocking dialogs (`ctx.ui.select/confirm/input/editor`, plus the PiChamber-specific `ctx.ui.form` which resolves with a values object keyed by field id) publish an `extension.dialog` event and stay pending until answered by the `extensions.respond` private command; every answer, timeout, abort, session close, or daemon stop publishes an authoritative `extension.dialog.dismiss` event before resolving the extension so every connected client removes the modal (timeouts resolve defaults, abort resolves cancellation, form answers travel as a sanitized `values` record and are rejected unless required fields, number bounds, select options, and checkbox values match the pending form); fire-and-forget calls publish `extension.notify`, `extension.status`, `extension.widget`, session-scoped `extension.editor`, and `extension.title`; extension errors publish `extension.error`; appended custom entries and displayed custom messages publish `extension.entry` / `extension.message`. `pichamber.ui` entries with a stable `id` are additionally mirrored into normalized `extension.ui` panel events (latest wins per id, `removed: true` unregisters) and `pichamber.app` entries into sandboxed `extension.app` app surfaces; extension live state is kept in per-session maps and included in both `sessions.open` and `session.snapshot`. The open response must cover every extension event at or below its `lastSequence`, so first attach cannot skip one-time startup statuses before the browser stream connects; reconnect snapshots rebuild the same live panels. TUI-only component replacement, footers, and themes remain intentional no-ops; standard RPC editor replacement and window titles are projected to the focused browser session. Pending dialogs are cancelled when the owning runtime hits idle disposal or daemon stop so no extension thread blocks forever. Unknown dialog responses return `{ resolved: false }` rather than throwing so a stale client retry cannot tear down the shared socket.
  - `createSessionDaemon(options)` starts/stops the authenticated local socket daemon and validates its endpoint and setup inputs. Test seams inject `createRuntime` for resident runtimes and `createServices` (default `createAgentSessionServices`) for transient per-mutation prompt services.
  - Default runtime: calls without a session id (providers, models, settings, and through them the model lookup of every orchestration spawn) run on the default runtime. Every switch of the default records it as the dormant session through `setDefaultRuntime`, so reopening never names an older session. When no default runtime is live, `startRuntime` adopts the dormant session if it is live again, forgets it when its JSONL or working directory is gone (deletion forgets it directly), and starts fresh in the daemon cwd when the requested directory no longer exists. A runtime that won the race for the same session becomes the default and keeps its lease. The losing runtime is disposed, or, when disposal fails, kept with the failed-create cleanups that delete and stop retry. A failed start releases the session lease only while no other runtime of the daemon owns or is opening that session. While a failed-create cleanup for a session is pending, no path (idle disposal, stop, delete) releases its lease; it goes once that cleanup has disposed its runtime (#164, #171).
- `session-replay.js` owns the byte- and count-bounded contiguous replay suffix (`MAX_REPLAY_EVENTS`, `MAX_REPLAY_BYTES`, `createSessionReplayLog`). It caches one serialized line per event for broadcast/replay reuse and reports contiguity (`canReplay`) without trusting filtered delivery.
- `daemon-process.js` is the detached private-process entrypoint. It reads the daemon credential from its owner-only sidecar, starts the socket, writes non-secret identity state only after readiness, persists an accepted ownership claim before acknowledging it over IPC, and removes only its own state on signal shutdown.
- `ipc-client.js` is the server-only authenticated request client. It owns JSONL framing and never exposes endpoint or credential values to callers.
- `runtime-registry.js` owns active runtime identities and session-local subscriptions. It rebinds the subscription after an SDK session replacement, rejects identity conflicts rather than displacing another runtime, and attempts every tracked disposal even when another disposal fails.
- `session-jsonl.js` validates cwd-scoped Pi JSONL before discovery. Create, rename and daemon startup require a valid session header per file (`validatePiSessionJsonlDirectory`); they do not read whole transcripts. `sessions.list` uses `listPiSessionJsonlDirectory` (header, first user prompt from a bounded 512 KiB head, latest rename). The listed name follows Pi's `SessionManager.getSessionName`: the latest `session_info` entry anywhere in the file, where an empty name clears it. A fork copies its parent's path including the parent's title, so a later rename can lie megabytes before the end; a fixed-size tail would miss it and list the parent title again after a restart or idle unload. Without a memo the reader therefore scans backwards from the end in raw byte chunks (`session-info-scan.js`, only lines containing the `"session_info"` marker are parsed) until the first rename or the end of the head scan; a large session that was never renamed is read once in full. The daemon passes one `createPiSessionListCache()` memo per process: a file whose inode, size and mtime are unchanged is not read again, a file that grew is searched only after the last complete line already scanned, after checking that it still starts with the remembered header line and that offset is still a line boundary. A shrunk, replaced or otherwise rewritten file, a trailing line that is still being written, and a file whose first prompt is not known yet fall back to the full read. Files in one directory are listed with at most eight concurrent reads. One file does not fail the listing of the others (#126): a file removed since the directory was read is absent, and any other failure (malformed header, unreadable file) skips it, logs only its error code (no path, no content) and marks the returned array `incomplete: true`. An unchanged malformed file stays in the memo and is neither read nor logged again until it changes. Lookups that list a directory (`findPersistedSession`, `orchestration/session-lookup.js`) treat an `incomplete` listing without a match as a failed lookup, not as absence. `sessions.list` passes the marker on as `incomplete: true` next to `sessions` (absent for a complete listing), and `GET /api/pi/sessions` forwards it to the client. Only a failure to read the directory itself fails the listing. Full-file validation remains on open of a specific session so a malformed body still fails that chat. Pi's SDK list is not the production list path because it scans every line of every log. Directory names match Pi's SessionManager encoding, including Windows drive letters and Git Bash/MSYS/Cygwin/WSL `/c/...` paths so PiChamber and the Pi CLI share the same JSONL sessions.
- `supervisor.js` resolves server-only overrides, creates the credential, serializes start/reuse/stop through an owner-only lock, validates daemon identity through `runtime.health`, forwards server-owned commands only after that identity check, and starts or stops the detached process. Reuse requires the ready-state sidecar `entrypoint` to match this checkout's `daemon-process.js`; a healthy same-profile daemon with a different entrypoint is claimed and then shut down through authenticated IPC so local `bun run dev` cannot keep answering `getSession` without the live-turn overlay. When the parent is Electron, the child is spawned with `ELECTRON_RUN_AS_NODE=1` so packaged Windows/macOS/Linux apps run the daemon as Node instead of a hidden second Electron GUI process.
- `../server/server-profile.js` derives one stable daemon profile per server: installed web is `web-p<port>`, development web is `web-dev-p<port>`, installed desktop is `desktop`, and development desktop is `desktop-dev`. `PICHAMBER_SERVER_PROFILE` overrides the derivation with a hashed `custom-<hash>` key so raw input never becomes a path, while preserving whether the launcher is a development build for stale-code replacement. The profile key is stable across restarts; the server instance id is a fresh UUID per launch. Development launchers (`scripts/dev-web-hmr.mjs`, `scripts/dev-web-full.mjs`, `cross-env` in the `dev:server` scripts, `PICHAMBER_ELECTRON_DEV`) explicitly mark themselves so stopping development can never terminate the installed daemon.
- `../server/cross-process-lock.js` serializes critical sections across servers sharing one data directory (exclusive create, owner nonce, dead-pid steal, bounded wait). It backs the daemon operation lock pattern and every shared read-modify-write store below.
- `session-lease.js` owns exclusive cross-daemon residency of one Pi session, keyed by canonical agent directory, cwd, and session id under `<agentDir>/.pichamber/locks/sessions/`. The lease is acquired before a resident `AgentSessionRuntime` is created and released after idle disposal, deletion, replacement, or daemon shutdown. Opening or deleting a session leased by another live daemon returns `SESSION_IN_USE` (HTTP 409) while the session stays visible in listings; opening one whose stored working directory was removed returns `SESSION_DIRECTORY_MISSING` once the lease shows no other daemon holds it, and aborting it then has nothing to abort and succeeds (#177); different sessions remain fully concurrent. Lease files from different `PICHAMBER_DATA_DIR` values still coordinate because they live under the shared agent directory.
- `../routes.js` registers authenticated public adapters before the generic proxy. It exposes only whitelisted runtime, project, session, provider-auth/configuration, settings, resource, small-model utility, and SSE event shapes; no browser response contains daemon paths, credentials, PIDs, headers, or socket framing. Session actions are path-selected, so an identity supplied in a request body cannot redirect a mutation. `POST /api/pi/sessions` projects the created detail through the same session-detail projector as `GET /api/pi/sessions/:id`, so extension items appended from `session_start`, the `streamEpoch` stamp, and extension UI snapshot state are returned rather than rejected; only a malformed detail is `DAEMON_PROTOCOL_MISMATCH`. `archive-store.js` persists PiChamber-only opaque session archive metadata atomically beneath the PiChamber data root and never edits Pi JSONL. `settings-store.js` keeps PiChamber new-session defaults separate from Pi settings.json. `/api/pi/small-model/generate` reads that sidecar and runs a bounded in-memory no-tools Pi session, so utility generation creates no visible or persisted session and exposes no model or credential details. `GET /api/pi/settings` copies leftover UI/desktop `defaultModel` / small / walkthrough strings into that sidecar when those sidecar fields are unset, then Sessions settings is the only editor. Sidecar `defaultThinkingByModel` is the per-model thinking map (`provider/model` keys). A stored global `defaultThinking` with a default model is copied onto that map key and dropped; global thinking without a default model remains a clamp-only fallback. `ui-settings-store.js` owns portable PiChamber preferences at data-root `settings.json` and host, device, and secret-bearing values at `runtime-state.json`. `/api/pi/ui-settings` merges both views for existing clients and splits writes through explicit field allowlists. It migrates an unscoped flat file once; after the portable scope marker exists, local fields found in `settings.json` are ignored rather than applied to the host. The route is not available through removed `/api/config/*` aliases. `session-folders-store.js` validates and atomically persists the restored sidebar's folder snapshot at `/api/pi/session-folders`; a missing snapshot is distinct from an empty one. `custom-themes.js` serves validated custom-theme candidates from `/api/pi/themes` with per-file partial-failure isolation. `model-config-store.js` atomically updates Pi's credential-blind `models.json`; literal keys continue through Pi auth and headers are write-only. `providers.config.get` returns `config: null` for a provider that is not in `models.json` (built-in catalog entries) and fails only when that file is present but malformed.
- `../event-stream.js` owns the `/api/pi/events` SSE connection lifecycle so `../routes.js` stays a thin adapter. Per connection it installs cleanup before `subscribe` is awaited (a client that leaves during the opening window cannot leak a daemon subscription; a late subscription is closed exactly once), funnels client disconnect, subscription error, and server shutdown through one idempotent cleanup, hands an `AbortSignal` through the supervisor to the private IPC subscriber, never writes a named heartbeat or a late frame to a dead response, and byte-bounds the response socket buffer (`res.writableLength`, default 8 MiB, aligned with the daemon replay budget) with the bound enforced BEFORE each write so no single frame overshoots it. A client that stops reading is disconnected recoverably — the stream ends and the client reconnects from its last accepted sequence for replay or an authoritative snapshot, so no event is silently removed from an otherwise contiguous stream, but frames still buffered when the disconnect fires are not promised as delivered; the reconnect replay is the delivery guarantee — while a healthy client's connection stays independent of the slow one. Every teardown is bounded: a `write()` that returns false starts a drain deadline (default 5s) that ends even a quiet never-draining client, and after `res.end()` a terminate deadline (default 5s) destroys the response, because `end()` alone only queues the FIN behind unflushed data and would otherwise leave a stalled socket open forever and hang server shutdown/close. The response `'error'` guard stays attached for the response's lifetime (idempotent; cleanup can complete while data is still in flight and a late unhandled `'error'` would crash the process). The registry tracks live connections so `registerPiRuntimeRoutes` can expose `closeEventStreams()` for server shutdown, ending active and still-opening streams (and their daemon subscriptions) before the HTTP server closes. The IPC subscriber removes its abort listener and destroys the opening or active daemon socket on cancellation.
- `orchestration/` owns session orchestration (#107, [ADR 0010](../../../../../../docs/adr/0010-orchestration-through-daemon-tools.md)). `session_list` and `session_read` report each session's state, the outcome and error of its last turn and, while it runs, an `activity` object (run duration, time since the transcript last changed, automatic retry with the provider error, a blocking dialog), so an orchestrator can spot a stuck worker without polling transcripts. `tool-contracts.js` defines the tools (`orchestration_capabilities`, `orchestration_digest`, `orchestration_takeover`, `session_spawn/list/read/send/wait/interrupt/stop/rewind`, `worker_report`) and their schemas; `worker_report` is for workers only (`orchestratorAllowed: false`, hidden from orchestrators' active tools), `orchestration_digest` for orchestrators only. Worker reports (#117): `worker_report` (`progress`, `question`, `blocked`, `ready`, `done`) is validated per kind and stored on the worker in one registry `update` (`recordReport`); a retry with the stored `clientRequestId` changes nothing. A `question` or `blocked` stays open as `worker.question` until a report or a `session_send` from the owner names its id in `resolves` (closed only after the send was accepted); one is open at a time, and a new one must name the open one, which it replaces. Every admitted input sets `worker.lastInputAt` and leaves the question open. A `done` report binds to its own run in the same `update` (`doneReported`), so the worker becomes `done` and frees its slot only when that run ends; without a run of this service it is only stored. A reported pull request is kept as `{ number, repository }` from the worktree's `origin`. Every run end stores `worker.snapshot` (`lastProgressAt`, the last turn's `lastError`, Pi's `getSessionStats` totals as `usage`, each with its time), so `orchestration_digest` reads the registry and the live channels only, never activates a session, shows `live: 'dormant'` without a resident runtime and `null` for anything unknown. Ownership and bookkeeping live in one durable registry, `<dataDir>/pi/orchestration-registry.json` (#118): `registry-store.js` replaces it atomically under the per-file lock and serialises every change through `update`, and fails on a malformed file instead of reading it as empty; `worker-registry.js` holds the pure document changes. A spawn is a journalled operation (`reserved`, `session`, `prompted`, `durable`) whose slot is reserved in the same `update` as the daemon-wide limit check and held until the proven end of the worker's last run. The same `update` claims the canonical directory (`canonicalDirectory`, realpath): one starting or active worker per directory across all daemons of the data root, also for a prompt to a finished worker (`ORCHESTRATION_CWD_BUSY`). The host gate (#119) runs in that same `update`, after the limit check and only for a new spawn, never a resume: with `orchestration.gate.enabled` (default on) it refuses with `ORCHESTRATION_HOST_BUSY` and the numbers in the reason while the 1 minute load is above the core count or fewer than `orchestration.gate.minAvailableBytes` (default 8 GiB) are available. `host-info.js` reads the numbers (`hostGateNumbers`, `os.freemem()` is MemAvailable on Linux); `orchestration_digest` returns the same `host` numbers with the worker count and limit. The worker's lineage entry carries the `opId`, so a crash at any step resumes or releases it: `session-lookup.js` finds the session through the resident runtimes and then the persisted sessions of the start's directory, with the read failure rule of `scanPiSessionJsonlHeaders` (a file removed after the listing is absent, any other read failure leaves the scan incomplete and it goes on with the other files; unlike that header scan, an unparseable entry is no proof either, since the lineage entry may sit behind it), a failed lookup, or a session file whose entries before the first message cannot be parsed, keeps the start undecided (`SESSION_LOOKUP_FAILED`), a worker whose JSONL never reached disk goes back to `reserved` with its slot and is recorded as `replaced`, so neither lookup adopts it again or lets it hide the recreated session, and a prompt step is not sent again when the transcript holds a user message with exactly the task's text (a transcript that cannot be read now leaves the start open with `ORCHESTRATION_START_UNDECIDED`). Every transitional record names its daemon process (`process-identity.js`: pid, kernel start time, instance), so a reused pid counts as dead; the dead-process check runs before every call, rechecks the stamp in the writing `update`, and finishes only records of dead processes. A stop whose process died keeps the worker and its slot until `session_stop` is retried. Every input (UI prompt and `session_send`) passes one admission contract (#125 round 5). `beforeSessionInput` only fails fast before the daemon activates a session and decides nothing. With the session resident and its lease held, right before `prompt()`, the daemon calls `admitInput`: one registry `update` checks a running stop, the limit and the directory and, for a `done` or `stopped` worker, takes its slot and directory as `admission` (`{ token, process, previous, since, state }`); another admission of the same process shares it, and one of another live process refuses with `ORCHESTRATION_WORKER_BUSY`. The ticket ends only with Pi's verdict on that prompt (`resolveInput`), never with a check made before the call, because Pi 1.1.0 runs input handlers between the call and its own streaming check (CONTEXT.md): `started` passes the slot to the run as a new `generation` (`commitStart`), counted once; `queued`, `handled` and a rejection end the ticket without a run, and once no ticket of the worker is open the admission's slot goes back and a settle that waited for the tickets applies. A settle applies the `done` rule only to its own generation, so a late settle of an earlier run changes nothing, and it waits while an admitted ticket has no verdict, since that input may start the next run. A prompt Pi accepts without a verdict (deferred while `agent_settled` handlers run) is `unresolved`: nothing is rolled back, the slot stays and the registry shows `admission.state: 'unresolved'` with `unresolvedAt` until its late verdict (Pi runs the deferred prompt again) or a stop; a watchdog (Slice 4) reports one that stays. Every registry step of a ticket names its admission token and applies only while the worker still shows that admission (#125 round 6): a run that `started` holds the admission's slot from its verdict until its own settle, so neither a settle of the run before it nor the end of a sibling ticket frees it, and when its `commitStart` fails nothing is rolled back: the run's next registry step (its done report or its settle) completes the commit as `completeStart`, so the report binds to the run's own generation and an earlier run's `done` never ends it (#125 round 7). A settle never sets `done` while the worker shows an admission. A stop ends the admission and makes every remaining ticket stale; a late `started` of a stale ticket confirms nothing, also not a newer admission, and aborts only its own run: the daemon binds each `started` verdict to the run Pi starts for it (`run-binding.js`, the agent's `AbortSignal` that is new one microtask after the verdict) and aborts it only while that signal is still the session's run, in one synchronous step. SDK assumption (Pi 1.1.0, `CONTEXT.md`): Pi starts the run in the same synchronous step that reports `started`; `run-binding.e2e.test.js` pins it. A verdict without its own run (another run took the agent first) aborts nothing. Each `started` verdict has its own start identity (the ticket token, with the order of the verdicts), fixed before the first await; several inputs may share one admission, so the admission is a grant of the slot and not the identity of a run (#125 round 8). `completeStart` returns a generation only for the same start and never hands an older start the generation of a later one; a done report and a settle freeze their run's start before the first await and apply only to it, with no fallback to the current generation, and a done report without a live run of this service records nothing. An `agent_settled` event is only a candidate: while the agent still has a `signal`, also an aborted one, a run is live, so the daemon drops the event before it publishes idle, ends a pending input or wakes the owner (`isSettleFinal` in `run-binding.js`). A bound signal permits an abort but proves no completion; an aborted run is not over until it settled, and a retry, `agent_before_settle` or a continuation makes a new signal without a new `started`. No settle, with or without a signal, ends a run's occupancy: only the end of the `prompt()` call that reported its `started` verdict does (`provenRunEnd` in `run-binding.js`; Pi 1.1.0 resolves it after the run, every retry and continuation and its `agent_settled` handlers, CONTEXT.md). The settle only stores the run's result, applied with that proof. A `started` verdict that bound no run of its own keeps its admission until its prompt ended. A late verdict (Pi ran a deferred prompt again) has no prompt of its own, so its run, aborted or not, holds the slot and directory as `hold` (`reason: 'unproven_run'`), reported as `ORCHESTRATION_RUN_UNPROVEN`, until the holding process is dead. A stale run that cannot be bound is not aborted (it may be another valid run). Every occupancy (`starting`/`active`, an admission, a hold) counts in the limit and in the directory check. Limit of this contract: Pi 1.1.0 gives no unique run identity and can emit `agent_settled` while another prompt's run is live. PiChamber frees a slot and directory only on a completion it can attribute; missing or contradicting evidence keeps the occupancy, which can lower capacity for good. Other workers stay protected; an unbound stale prompt is no reason to abort their run. No signal is not proof of completion either (a run waiting in its retry backoff has none), so an attributed completion stays an SDK assumption pinned by `run-binding.e2e.test.js`. Detecting and reporting such held claims belongs to Slice 4; neither another settle nor a timeout confirms their end. A registry write that fails while recording a start likewise rolls nothing back (a held slot is better than a rolled back worker) and is published as `session.error` `ORCHESTRATION_ADMISSION_UNRESOLVED`. The reconcile releases the admission and the hold of a dead process; its runs ended with it. A session without lineage passes even when the registry is unreadable; workers and tool calls then fail. `contract-validator.js` checks every argument against the published schema (`INVALID_ARGUMENT`), and a caller whose session no longer exists gets `ORCHESTRATION_CALLER_GONE`; a lookup that failed on storage errors is not proof of absence (`findPersistedSession` marks it `incomplete`; only a missing sessions root, store or file counts as absent, a store that vanished mid-scan is skipped, not the end of the scan, and a same-id file that does not validate only marks the lookup incomplete while the scan goes on to a later valid one) and fails with the retryable `SESSION_LOOKUP_FAILED`, so no credential is revoked for it. The caller of `orchestration.call`/`caller` and every session a tool uses (read, send, wait, abort, the old owner a takeover checks, a resumed start's worker during its prompt step, a parent whose legacy workers are imported, and the owner a wake is sent to, until Pi accepted it) hold the idle guard (`holdSession`) like direct requests for the whole use and are disposed again when idle. The guard only keeps a disposal from starting, so a runtime whose idle disposal already runs is not live for orchestration (`getLiveRuntime`): its users wait for the disposal in `activateSession` and reopen the session, and a wake is never sent into a runtime that is being torn down (#190). A spawn retry while the first task is still being accepted shares that outcome, and each send holds its own pending token, so a receipt retry never ends a newer send's run. A worker whose first task Pi rejects is stopped with `task_rejected` and frees its slot. `policy.js` decides every call: workers get only `childAllowed` tools, `session_stop`, `session_rewind` and `worker_cleanup` need ownership, `session_send/read/interrupt` reach any session. `session_rewind` (#116) moves an idle worker of the caller to an earlier entry of its active branch through the daemon's `navigateSession` (the function behind `sessions.navigate`: alias resolution, Pi's `navigateTree`), optionally prompting it in the same call; it refuses `ORCHESTRATION_SESSION_BUSY` while the worker runs, retries, starts, waits for input or has a direct input Pi has accepted but not yet turned into a run (`activity.inputActive`, from `activeSessionInputs`), and `SESSION_TREE_NOT_FOUND` for an unknown entry. A repeated `clientRequestId` replays the first answer (`deduplicated`) without navigating again (per process, like the send receipts), and a different entry or prompt under it is `OPERATION_PAYLOAD_MISMATCH`. It undoes no file change or command. `session_read` lists the messages of the active branch with their `entryId`. `orchestration_takeover` moves all workers, open operations and retry keys of an idle orchestrator to the caller in one `update`; it refuses with `ORCHESTRATION_TAKEOVER_BUSY` while the old orchestrator runs, is resident in another daemon, a start step of it runs in a live process, or a stop of it is still aborting a worker (importing an old orchestrator's JSONL child entries once), and a late step write or stop claim of the old owner fails with `ORCHESTRATION_OWNER_CHANGED`; a stop claim carries its own token, so only that stop finishes, releases or reports it (a stop that lost its claim fails with `ORCHESTRATION_STOP_CLAIM_LOST`). A second stop of a worker shares the stop running in the same service, and a live claim of another process is never replaced (`ORCHESTRATION_STOP_BUSY`). A stop waits for the verdicts of inputs admitted before its claim and aborts the run they started. When Pi accepted an input that has no verdict yet, the stop ends the worker but keeps its slot and directory as `hold` (`reason: 'unresolved_input'`) and names it in `held`, since neither a local abort nor a stale ticket proves that Pi will not run it; the hold ends with that input's verdict (`queued`, `handled`, a rejection) or with the proven end of the run it started. A run whose verdict arrives after the worker stopped is aborted at once and holds the slot (`stale_run`) until its prompt proved its end; without that proof the hold stays (`unproven_run`). Inputs arriving behind the claim fail with `ORCHESTRATION_WORKER_STOPPING`. `orchestration-service.js` handles the tools, idempotent spawn by `clientRequestId` through `requestKeys`, stop (abort first; a failed abort keeps the worker and its slot and fails with `ORCHESTRATION_STOP_FAILED` naming the stopped and failed ids, a session that no longer exists counts as stopped, and so does one whose working directory was removed: its abort is a no-op, #177). Wakes (#117, `wakes.js`, in memory) replaced #107's result delivery: a worker's run end (`run_finished`, or `run_failed` with the provider's error line when the run ended in an error after Pi's retries, or `done` when it ends the run a `done` report bound to), a `question` or `blocked` report addressed to the orchestrator (`question`, `blocked`; a report with `audience: owner` queues nothing), a `ready` report (`ready`) or an extension dialog opened in it (`question`), and a busy worker without an open dialog and without message, tool or report activity for `watchdog.stallAfterMs` (`stalled`, once per episode, checked on a 15 s tick between the daemon's `start` and `stop`) queue one event `{ sessionId, kind, reason, at }` with a one line reason of at most 200 characters. Routing (#156): the last writer decides. ## Protocol and security invariants

- Each profile owns its daemon artifacts: `<dataDir>/pi/daemons/<profileKey>/` holds the credential, `daemon-state.json`, and `operation.lock`; the endpoint is `<runtimeDir>/pi-daemons/<profileKey>/daemon.sock` (or `$XDG_RUNTIME_DIR` equivalent); per-profile logs append to `<dataDir>/logs/pi-daemon-<profileKey>.log`. The state sidecar records `profileKey`, `serverInstanceId`, `serverPid`, `daemonId`, `runtime`, and `buildId` alongside pid, endpoint, and entrypoint. A pre-profile legacy daemon is never adopted, unlinked, or signaled; only its dead pid record is best-effort removed.
- The endpoint is a Unix domain socket on POSIX or a Windows named pipe. TCP endpoints are rejected. Listeners and clients connect with IPC `path` options so Windows `\\.\pipe\pichamber-pi-session-daemon-<owner-key>-<profileKey>` works the same as a POSIX socket path. `PICHAMBER_PI_SESSION_DAEMON_ENDPOINT` still overrides the socket path, but the credential, state, and lock stay per-profile: a profile never adopts, unlinks, or signals an endpoint it cannot authenticate and identify as its own, and the conflict surfaces as `DAEMON_ENDPOINT_UNVERIFIED`.
- POSIX socket parent directories are mode `0700`; the socket is created mode `0600`. An existing endpoint fails startup rather than being unlinked without daemon-identity verification. Windows named-pipe ACLs are not yet equivalent owner-only OS permissions; credential authentication remains mandatory.
- The daemon credential and non-secret state sidecars are mode `0600`; their per-profile parent directory and the operation lock serialize start/reuse/stop. Exclusive lock create writes the owner pid in the same step. A leftover empty or malformed lock, a dead owner pid, or Windows `EPERM`/`EACCES` on exclusive create is retried and stolen after a short freshness window instead of failing as `DAEMON_LOCK_UNAVAILABLE`. Sidecar `chmod` failures on Windows are ignored after the file exists so readiness is still recorded. Health identity includes the daemon PID, profile key, and daemon id, and all three must match the state sidecar before the supervisor reuses a process. Reuse also requires the ready-state `entrypoint` to equal this host's `daemon-process.js`; a missing or different path is not identity-compatible and is replaced after a claim.
- Ownership transfers through authenticated `runtime.claim` only after the previous server PID is no longer live. The daemon persists the new `serverInstanceId` and `serverPid` to its state sidecar before acknowledging the claim, so its in-memory owner and discoverable owner cannot split. Shutdown goes through authenticated `runtime.shutdown` (profile, daemon id, and current owner instance must all match) before any signal; a stale server whose daemon was claimed receives `DAEMON_OWNERSHIP_MISMATCH` and terminates nothing. A direct signal is used only after authenticated health and ownership checks prove that the sidecar PID is this profile's daemon (or for a child the supervisor just spawned during failed startup).
- Shared writable state is coordinated, not merely namespaced. Pi prompt, context, settings, and model writes serialize through `<agentDir>/.pichamber/locks/pi-config.lock`; `models.json` additionally serializes in its store. PiChamber data-root stores (`pi/settings.json`, `pi/snippets.json`, `pi/session-archive.json`, `pi/session-folders.json`, root `settings.json` and `runtime-state.json`, STT config, remote-client and pairing stores) serialize read-modify-write through per-file locks with atomic replace; `session-folders.json` additionally rejects a stale `updatedAt` snapshot as `SESSION_FOLDERS_STALE` (HTTP 409) instead of silently overwriting newer folders. Passkeys, the JWT secret (exclusive create with re-read), the tunnel token, and git identities use atomic replace. Cross-daemon config staleness is bounded by idle runtime disposal (five minutes), which recreates runtimes from disk; there is no cross-daemon live-reload generation yet.
- The public health route deliberately whitelists its response fields (state, protocol version, capability names, and the opaque public `streamEpoch`). It never returns a daemon endpoint, credential, PID, cwd, agent directory, or transcript data. Public transcript and event projections preserve daemon-redacted assistant error messages so the UI can distinguish provider/runtime failures instead of reducing every failure to `ASSISTANT_ERROR`.
- A client must send an `authenticate` frame carrying the host-private daemon credential before it can issue a request. Credentials are never logged or returned.
- Frames are LF-delimited JSON. One frame has a 16 MiB maximum. Complete frames are parsed before the client bounds the remaining incomplete frame. Invalid JSON reports `MALFORMED_DAEMON_RESPONSE`; an oversized response reports `DAEMON_RESPONSE_TOO_LARGE`. A malformed, oversized, unauthenticated, or invalid request closes the connection.
- Extension widget lines (`ctx.ui.setWidget`) are bounded: at most 100 lines, each cut to 2000 characters. One position is the documented protocol exception: line 0 of the `subagent-async` widget, when it starts with `PI_SUBAGENT_ASYNC_JSON:` (the bounded async run snapshot pi-subagents sends to RPC hosts), keeps its JSON whole up to the producer's 32 KiB serialized cap, because cutting that JSON makes it unreadable. A prefixed line under another key or at another index is cut at 2000 like any other, so a widget stays within its old size bound. `../extension-protocol.js` owns the limits (`clampExtensionWidgetLine(key, index, line)`, `extensionWidgetLineLimit`) and the bridge computes the clamped lines once, so the live `extension.widget` event and the reconnect mirror (`sessions.open`, `session.snapshot`) carry the same value; `../routes.js` applies the same limit when it projects both to the browser. A line past its limit is truncated, never repaired, and the UI treats an unparsable snapshot as unavailable. The widget key `subagent-inspect` carries on-demand inspect replies that hosts must not render; the daemon forwards it like any widget and the UI drops it.
- The private core commands are `runtime.health`, `projects.list/select`, `providers.list/config.get/models.set/models.add/status/login/login.respond/login.status/logout`, `settings.get/set`, `resources.list/update/prompts.create/prompts.update/prompts.delete`, `extensions.list/respond`, `orchestration.call`, `orchestration.prWatch`, `orchestration.overview`, `orchestration.answer`, `orchestration.resolve`, and session list/create/open/messages/rename/delete/tree/navigate/fork/clone/prompt/steer/followUp/sendReceipt/abort/model/thinking/compact operations. Resource lists use opaque IDs and never disclose server paths. Only top-level Pi prompt templates and applicable AGENTS.md sources are editable; package/path resources and skills are browse-only. Prompt-template mutations resolve against the caller's explicit effective directory, reject stale and cross-directory opaque IDs, enforce project trust for project prompts, serialize create/update/delete operations, preserve existing files on validation or write failure, atomically reserve new destinations without overwriting concurrent writers, use temporary-file persistence with cleanup, preserve unknown frontmatter fields (for example `argument-hint`) when editing description or content, and for rename validate the destination name and scope, reject collisions, write the destination atomically, remove the source only after success, and roll back the destination when source removal fails. A committed prompt mutation never disposes a session runtime: affected idle sessions use Pi's identity-preserving `session.reload()`, while streaming, compacting, and extension-command sessions finish first and reload at their next safe lifecycle edge. Global prompts refresh every resident runtime; project prompts refresh only runtimes in that directory. Mutation responses merge freshly discovered editable prompts from transient per-mutation services (never retained; Pi 0.84.1 exposes no dispose on AgentSessionServices/ModelRuntime/ResourceLoader/SettingsManager — file reads plus a cleared create-time timeout, no watchers/intervals/listeners, so dropping the reference lets GC reclaim it) with live package/path/extension resources so the Settings page reflects the committed file even while runtime activation is deferred. `providers.refresh` touches only live runtimes; the returned catalog always comes from the active runtime via `providers.list`. Generic non-prompt resource writes share the serialized resource-mutation queue and commit through an atomic replace even while a session is active. The daemon returns `deferred: true` and recreates resident runtimes after they become idle; a new session reads the committed file immediately. If immediate recreation fails after a committed write, the response still reports deferred activation and the daemon keeps the recreation queued for a later safe edge. Project trust changes are persisted in Pi trust.json and use the same deferred runtime recreation; project-local extensions load through Pi's own trust flow once trust is resolved. Provider login submits API keys only across authenticated private IPC or brokers Pi's OAuth/device/manual-code interaction; public projections contain only opaque login IDs, prompts, URLs/device codes, model catalog/configuration, and stable states, never credentials or write-only headers. `providers.models.set` atomically persists Pi's `models.json`; a busy runtime returns `deferred: true` and is rehydrated after all active sessions are idle, while a new session sees the catalog immediately. `providers.models.add` appends one model (`id` required; optional `name`, `reasoning`, `thinkingLevelMap`, `input`, `contextWindow`, and `maxTokens`) atomically without replacing the provider. The model configuration store owns normalization and validation. The daemon rejects duplicate or unavailable live models, seeds a missing file provider only from authoritative live metadata when safely representable, rejects extension registrations with an explicit `models` array, and uses the same deferred recreation as `providers.models.set`. A successful recreation publishes a provider-catalog invalidation so connected settings views load the new authoritative catalog. Provider edits preserve unexposed existing model metadata server-side while public projections remain credential-blind. `providers.list` projects only catalog and authentication-status metadata, including Pi-supported `thinkingLevels` (`null` map entries hidden, `xhigh`/`max` opt-in). Session thinking overrides are clamped to the live model's supported levels. `sessions.list` checks each cwd JSONL header (not the full transcript) so a project with large session logs cannot spend tens of seconds on startup. SDK `SessionManager.list` is not used for that path; `listPiSessionJsonlDirectory` reads a header, a bounded prefix for the first user prompt, and a tail for the latest rename. Each listed row whose runtime is resident in this daemon (including unpersisted resident sessions) carries `live: { lifecycle, sequence, retry?, runStartedAt?, serverNow }`, sampled synchronously with the current event `sequence` from the same retry/streaming/run-start state as snapshots; rows without a resident runtime carry no `live`, which clients treat as unknown rather than idle. Concurrent lists of the same directory share one in-flight result. Concurrent `sessions.open` of the same id share one in-flight runtime create; a duplicate that finishes later disposes itself and returns the registered runtime instead of `SESSION_RUNTIME_CONFLICT`. Full-file JSONL validation stays on open of a chosen session. The browser explicitly selects an existing user-chosen project directory before listing it; the daemon's startup cwd is an internal fallback, not a user-visible default project. Unnamed persisted sessions use their first prompt as a readable list title when available. `sessions.open` and `getSession` project the last assistant `provider`/`model`/`thinkingLevel` onto the session record so reopening a chat keeps that cache identity. `sessions.open`, navigate, fork, and clone return a tail page bounded by both projected-message count and serialized bytes. `sessions.messages` reads older pages with an opaque before-cursor. A page that starts inside a tool loop repeats the owning user message as a grouping anchor; browser merging deduplicates that overlap. Persisted tool results are indexed across the active branch before paging, so a paged assistant tool call still receives its matching final result. Session selection validates a persisted JSONL path before Pi opens it; inactive mutations are never directed by a browser-supplied path. `sessions.open` first checks a caller-supplied directory through its bounded header list, so an ordinary project-scoped open neither walks every directory in the agent store nor adopts a same-id session from another directory. Directory-less deep links resolve by Pi's `timestamp_<id>.jsonl` filename before broader SDK-list and header-scan fallbacks. Directory-wide JSONL checks on list/create/startup are header-only; full-file validation stays on open of a chosen transcript. Attachment paths originate in the server-local upload map and cross only private IPC into Pi's tool context. Pi may persist or echo those paths in its authoritative JSONL transcript, so every public projection redacts them recursively: session titles/previews, user and assistant text/thinking, tool arguments, errors, snapshots, and live message events never expose the server-local path. Persisted projection first checks for the attachment marker, then redacts matching tokens with a delimiter scan whose work stays linear for large encoded strings and tool payloads. The daemon maps Pi message lifecycle, deltas, tools, queue changes, model/thinking, compaction, interruption state, and session title updates (`session.updated` on create-with-title, first-prompt auto-title, and rename) to canonical events. Session deletion publishes an explicit `session.deleted` event; archive and directory moves keep the id and never publish it. Pi `model_select`, `thinking_level_changed`, and `session_info_changed` events are authoritative for model, thinking, and session-name changes made by extensions, the TUI, or another client. The bridge observes Pi provider registration and label writes because Pi 0.84.1 emits no corresponding session events: provider mutations publish a catalog invalidation, and label mutations invalidate the bounded session-tree projection. `ctx.reload()` clears old extension UI state, reloads Pi resources, and invalidates provider/resource/command catalogs. `ctx.shutdown()` disposes only the requesting idle session runtime after its command or turn settles; it never stops the shared daemon or unrelated sessions. Compaction events preserve Pi's manual/threshold/overflow reason, active/retrying/terminal phase, retry timing, redacted failure, compact-and-retry intent, and pre/post token estimates. The latest state is included in `getSession` and reconnect snapshots; after daemon restart, the latest persisted Pi `CompactionEntry` restores completed feedback without treating history as live work. Tool events carry redacted input arguments, cumulative partial-output snapshots, final output, error text, renderer metadata (edit diffs, truncation notes), and server start/end timestamps plus a `serverNow` sample so clients with different clocks can normalize elapsed time. Active and recently completed tool parts retain their start timestamps in the daemon's bounded in-memory timing cache, so `getSession` hydration keeps timers consistent across clients and browser reloads until the daemon restarts. Pi loads skills with the ordinary `read` tool. The daemon matches those read paths against the active runtime's authoritative `resourceLoader.getSkills()` catalog and adds path-free `metadata.pichamber.skill.name` for live events, hydrated history, and reconnect snapshots. PiChamber uses that metadata for its compact Skill row and Settings navigation; an arbitrary file named `SKILL.md` remains a normal read. `nested-tool-calls.js` owns the one pi-fabric-specific projection: pi-fabric runs every Pi tool as a nested call inside a single `fabric_exec` call, so for that tool the daemon replaces the raw `details.audits`/`details.trace` with a neutral `metadata.nestedCalls` list (`name`, `input`, `success`, `output`, `error`, `metadata`, `startedAt`, `endedAt`; at most 200 calls, 50,000 output characters each). It reads `audits` first (live updates and settled results) and falls back to `trace.operations`. A nested Pi tool result's `details` (the edit diff) becomes that call's `metadata`, so the UI renders it exactly like a native tool. Details without a nested list, and every other tool, pass through unchanged. The projection runs inside `mergeToolPresentationMetadata`, so live events, hydrated history, and reconnect snapshots agree. Persisted `toolResult` entries merge into their assistant `toolCall` parts as output/error/end time so hydrated sessions render complete tool cards; tool-result entries never surface as standalone messages. Assistant message projections and start events carry the owning user-message id so the restored turn renderer can group and display replies; all assistant entries in a tool loop and every retry/compaction continuation remain attached to the latest user turn until `agent_settled` closes the run. Assistant message projections also pass through Pi's per-turn `Usage` (input, output, cacheRead, cacheWrite, totalTokens, and the same five numeric cost fields). The daemon sanitizes the raw payload through `projectUsage` before publication: every numeric must be finite and non-negative, the whole object is omitted when any field is missing or wrong type, and unknown keys are never copied. The `assistant.message.end` event carries the same sanitized usage so the last turn updates without waiting for a full `getSession` refetch. The public route whitelist re-applies the same sanitizer on each projection so a stale or malformed payload from a different daemon version cannot surface as `NaN` or `Infinity` in the reducer.
- Live `message_start` events use daemon-generated browser message IDs because Pi has not appended the corresponding session entry yet. Pi agent-core emits streaming assistant starts as shallow copies, not as the finalized object it later persists. At `message_end`, `message-entry-aliases.js` therefore rebinds the synthetic ID to the finalized event object, then maps that object by identity to Pi's appended entry in a microtask. `sessions.navigate` and `sessions.fork` resolve the mapping after stripping any part suffix. Alias keys include cwd and session ID, survive idle runtime disposal of persisted sessions, and clear on explicit session deletion, confirmed ephemeral expiration (which publishes `session.deleted`), or daemon shutdown. Hydrated message projections continue to use the Pi entry ID directly.
- Each event and reconnect snapshot has a monotonic sequence. Replay is capability-negotiated: the subscriber stamps its cursor with the `streamEpoch` it was established under, a marker-less cursor fails as `DAEMON_PROTOCOL_MISMATCH`, and a cursor from a retired epoch resyncs from a snapshot instead of replaying — even when this daemon's sequence numerically overtook the old cursor, replaying from it would silently skip the head of the new space. Every event, snapshot, and health result carries an opaque random `streamEpoch` regenerated on every daemon process start (never derived from daemon id, profile key, pid, or any private identity); `runtime.health` advertises the `events.streamEpoch` capability, session reads stamp it so clients can reject stale-epoch responses, and a snapshot published because the cursor could not be replayed is additionally stamped `resync: true` as a recovery baseline. A reconnect replays the retained contiguous suffix after its cursor when available, otherwise it receives an authoritative `session.snapshot`; unavailable runtimes are not represented as empty sessions. The suffix lives in `session-replay.js` and is bounded by both count (1,024 events) and encoded wire bytes (8 MiB): eviction removes whole oldest events first and never truncates content, each event is serialized once and the cached line is reused for live broadcast and replay, and live delivery stays full-fidelity even for events too large to retain. The byte budget counts encoded wire bytes, not heap, and snapshots assign sequence numbers without replay insertion so numeric gaps from private snapshots are intentional. A single oversized event clears the retained suffix without being retained, an empty ring never replays, and a cursor beyond the latest sequence resynchronizes from a snapshot; contiguity is judged on the global suffix while delivery stays session-filtered, so a filtered client never replays through a gap. A missed suffix recovers through `session.snapshot` plus `sessions.open` hydrate, which re-reads persisted entries for tool finals and lifecycle.
- Prompt, steer, and follow-up requests acknowledge acceptance only after the Pi SDK preflight signal (session.prompt with preflightResult(true)); the daemon owns the still-running turn promise and publishes any asynchronous rejection as `session.error`. A preflight rejection (preflightResult(false)) propagates as the request rejection so dedup never caches it as accepted and the operation id stays reusable. Pi 1.1.0 resolves a prompt made while `agent_settled` handlers run without a preflight signal and starts its run afterwards (CONTEXT.md); the daemon answers it as accepted, and a worker's admission stays `unresolved` until the late signal arrives. Plain text uses prompt() with expandPromptTemplates:false and source:extension plus images; slash input keeps source:rpc. Pi can emit the live user-message start before that message is branch-readable, so the daemon queues each accepted prompt's path-free file metadata per delivery kind (`prompt`/`steer`/`followUp`) and adds it to the matching user start. SDK `queue_update` shrink is the authoritative owner of the next user start (steering drains before followUp regardless of send order); direct starts emit no shrink and fall back to oldest-by-generation. Requested `steer`/`followUp` always travels as SDK `streamingBehavior` (ignored while idle) so an idle arrival that races another sender still queues. Retention is decided at resolution from authoritative runtime state (`isStreaming` or SDK queue non-empty, never for handled extension commands); only queued resolutions keep metadata until their per-delivery start, all other completions clean a still-pending entry (an extension command that never emits a user start). The browser can render the attachment footer immediately without exposing bytes or server paths, while later hydration remains authoritative. An extension command may resolve without starting an agent turn, so completion of its non-streaming prompt promise publishes the idle lifecycle boundary that Pi does not emit as `agent_settled`. Pi notifies extensions of model switches (`model_select`) but not session subscribers, so that same completion edge also reconciles a changed live model into `session.model` before the idle boundary; thinking already emits `thinking_level_changed` to subscribers and needs no reconciliation. A registered extension invocation is not used for automatic first-prompt naming: an extension-only empty session remains unnamed unless the extension names it, and the first later conversation prompt supplies the derived title. Classification uses the active Pi runtime's registered extension commands, not a browser claim. Manual compact requests likewise acknowledge startup instead of holding the public/private request open for the summarization call; the daemon-owned promise reports its outcome through `session.compaction`. A second compact request while Pi is compacting fails as `SESSION_BUSY`, and optional `/compact` instructions pass to `AgentSession.compact(customInstructions)`. A later prompt on the same session invalidates an older send rejection so it cannot error the new turn. If the rejected send left Pi streaming, the daemon aborts it. Steer/follow-up against an idle session starts a new prompt instead of `SESSION_NOT_RUNNING`. Agent and compaction completion are never held behind the 30-second public/private request budgets. Pi retryable provider failures remain live: an `agent_end` with `willRetry` does not publish terminal `session.error`, and `auto_retry_start` projects Pi's attempt, next-attempt time, and redacted error text through `session.lifecycle: retry`. Retry metadata is retained in reconnect and `getSession` snapshots until the next `agent_start` begins the attempt. `agent_settled` remains the authoritative idle boundary after retry success, exhaustion, or cancellation and clears the run's user/assistant ownership.
- Send-intent deduplication (`send-operation-registry.js`) owns the authoritative execution boundary for prompt/steer/followUp: the client labels each intent with a stable `operationId` and the health-verified `streamEpoch`, the daemon claims `kind + sessionId + operationId + streamEpoch` BEFORE Pi activation, and an identical same-epoch retry returns the original acceptance receipt (`{ accepted, messageId, deduplicated: true }`) without invoking Pi again. A concurrent duplicate of a still-pending intent shares the original outcome; the same full key with a different payload (text, model, thinking, message id, or attachments) fails as `OPERATION_PAYLOAD_MISMATCH` (HTTP 409). An intent from another daemon lifetime fails as `STALE_STREAM_EPOCH` (HTTP 409) before Pi or attachment-consumption side effects. The same id on a different kind or session is a different intent and executes independently, never a mismatch. Only acceptances are retained: request-path rejections happen before Pi runs (nothing executed, id reusable) while pending duplicates still share the original rejection, and every claim settles so pending duplicates never hang. Retention is bounded: receipts expire after `sendOperationTtlMs` (default ten minutes) and at most 1,024 accepted receipts are retained (oldest evicted to a bounded expired tombstone); pending claims are bounded separately (256 entries, never expired while active, new distinct pending past the bound fails as `SESSION_BUSY`). An expired or evicted id reports `expired` and a retry with the same id fails as `OPERATION_EXPIRED` (HTTP 410), never an automatic re-execution — callers must use a new operation id. `sessions.sendReceipt` is the exact read-only receipt lookup for an uncertain send: it requires the full `kind + sessionId + operationId + streamEpoch` identity; a missing epoch returns `unknown`, never invokes Pi, and returns `accepted` (retained receipt), `pending`, `expired` (seen but retention gone, outcome unknown, never assume success), or `unknown` (never seen in this retention window, tombstone pressure, post-restart, or rejected before Pi ran). The registry is in-memory per daemon process with bounded tombstones (`expired` degrades to `unknown` under pressure): there is no lifetime receipt guarantee, only within the retention window. A restart loses receipts, but the replacement daemon rejects the retired epoch instead of replaying the old intent. Receipt lookup and replay protection remain separate read-only contracts.
- Registry keys combine the SDK session ID with its cwd. A replacement subscription is rebound to the replacement session so old-session events cannot be published under the new identity. A collision is a visible error; it never replaces or disposes an unrelated runtime.
- After `agent_settled` or a terminal compaction that will not resume the turn, the daemon disposes an idle runtime after five minutes (injectable for tests). View-only access (`sessions.open`, `sessions.messages`, `sessions.tree`, plus navigate/fork/clone/abort/model/thinking/rename settlement) arms the same lifetime through `touchIdleDisposal`, so browsing old sessions without prompting cannot grow the registry unboundedly while the UI keeps only a bounded transcript cache. Disposal never deletes Pi JSONL; when the assigned session file exists on disk, the daemon remembers the selected session file and recreates that runtime on the next private prompt or open. When the assigned JSONL is positively absent (stat reports ENOENT only, determined after dispose while the resident lease is still held and before any release), the session is ephemeral: after a successful lease release the disposal clears matching dormant state plus the same safe per-session auxiliary state as explicit deletion where applicable (messageEntryAliases for cwd/session, retry/compaction/run-start/shutdown) and publishes the existing `session.deleted` event so connected clients remove it. Publication happens only after a successful release, which closes the cross-daemon recreate race. A missing/throwing getSessionFile or a non-ENOENT stat failure cannot prove absence and never claims deletion, a failed disposal retains ownership (registry entry, lease, and global runtime) without emitting deletion, and persisted sessions keep dormant state for reopen. The touch clears first and re-arms only when the session is resident and idle-safe, so a read cannot race a pending operation and a repeated open extends the deadline. Agent and compaction starts cancel pending disposal, and prompt/compact entry clears it before activation. The timer refuses to dispose a session while `isStreaming` or `isCompacting` is authoritative, while a send is in flight (`activeSessionInputs`), while a resource reload is pending or running, while a provider retry is scheduled, or while compaction is running/retrying, or while async subagents are live (below); pending extension dialogs are instead cancelled with an authoritative dismiss event. A read or prompt that arrives during an in-flight disposal waits for it and reopens from JSONL instead of adopting a dying runtime. There is deliberately no acquisition-path eviction: capacity pressure alone never disposes entries that are actively mounting.
  - Async subagent hold: pi-subagents stops watching for async results when its session shuts down, and a resumed session only delivers them at the next user turn, so disposing a session whose subagents are still working loses the completion. The idle timer therefore also refuses while line 0 of the session's mirrored `subagent-async` widget (`session-daemon/subagent-async-activity.js`, `hasLiveSubagentRuns`) is a version 1 `pi-subagents.async-status-snapshot` with at least one top-level run in state `queued` or `running`. It reads the same mirror clients get and parses nothing for sessions without a hold. A line that does not parse, another version, no live run, a removed widget, or the snapshot on another key or line never holds. There is no polling: the first refused disposal (or refused re-arm after a view-only access) starts one cap timer, and each later `subagent-async` widget event of a held session checks the mirror again; when no run is live any more the hold ends and the normal idle timer is armed through `touchIdleDisposal`. The cap is `subagentHoldCapMs` (default six hours, injectable like `idleTimeoutMs`) from the first refusal: it is not restarted by snapshot updates or reads. At the cap the hold stops applying until the snapshot is inactive again or the runtime is gone, so a hung run cannot keep a runtime in memory indefinitely, and the session is disposed as usual if no other guard (streaming, compaction, retry, send) refuses. The hold is cleared on disposal, deletion, and daemon stop.
- Ephemeral sessions: Pi's `SessionManager` defers JSONL creation until the first assistant message, so `sessions.create` alone stays ephemeral (untouched sessions vanish on restart by design). A rejected first prompt likewise persists nothing: the runtime stays resident and retryable until normal idle disposal, which reports the session as deleted when its assigned JSONL is positively absent (see above). Failed `sessions.create` cancellation and lease-acquire failures dispose without persisting and release (or never hold) the lease. Model/thinking setup failures after lease acquisition dispose first and release only after successful disposal: a disposal rejection retains `{ runtime, cwd, sessionId }` in daemon-owned pending failed-create state without releasing ownership, registering the runtime, or installing dormant state, while still throwing the original model/thinking error; `sessions.delete` retries its session entry and daemon stop retries all entries (dispose-first, release-after-success, failed retries stay pending without releasing ownership, entries removed only when still current, disposal exactly once).
- A startup validation failure writes only a stable failure code to the owner-only non-secret state sidecar. It never records a transcript, session path, or credential. The supervisor surfaces that code as unavailable instead of claiming an empty or idle session.
- After a forced crash, the next health, request, or subscription probe re-runs supervised startup. Each private health probe uses the supervisor's five-second operation budget; it must not inherit the general 30-second command timeout and hold every browser request until the browser aborts. Daemon readiness has its own 15-second bounded budget, separate from the shorter probe, lock, and shutdown budget, because loading Pi settings and provider/model catalogs can legitimately exceed five seconds. The supervisor removes an existing POSIX socket only when its recorded daemon PID is dead, the endpoint is a socket, and authenticated IPC deterministically refuses or times out. An endpoint that responds, authenticates incorrectly, returns malformed protocol data, or cannot be classified remains `DAEMON_ENDPOINT_UNVERIFIED`.
- The web server creates its supervisor after HTTP listen so the profile key uses the bound port, then warms it without awaiting Pi provider/model initialization. A first request arriving during that warmup shares the supervisor's `startPromise`. The bound profile key travels back over the `pichamber:ready` IPC message and into the CLI instance file; `pichamber logs` uses that key to include the matching private daemon log, while `--json` and `--quiet` serve output still carries only the port.
- The daemon owns the runtime after clients disconnect. Disconnecting the web-server client cannot stop active Pi work.

## Merge guard

Workers and marked orchestrators never merge into or push to `main` (#20); the owner does. `dev` and every other branch stay open, because workers merge into `dev` under the owner's standing approval. Unmarked sessions, the owner's own, are not guarded.

- `orchestration/merge-guard.js` is the pure rule. `judgeCommand(command, { cwd, shell, facts })` splits a `bash` or `powershell` command into the commands the shell runs (chains, pipes, new lines, subshells, `$(...)` and backticks, `bash -c`, `pwsh -Command`, `eval`, prefixes like `env`, `sudo`, `timeout`), following `cd` and `git -C`, and ignores quoted text, comments and here-documents. It returns `allow`, `block` with a reason, or `need` with the facts it cannot know from the text: the current branch and its upstream (`git push` without a refspec, or with `HEAD`), the base of a pull request (`gh pr merge`, `gh api .../pulls/<n>/merge`), the base of a pull request node id (a GraphQL `mergePullRequest` or `enablePullRequestAutoMerge`). Refspecs onto `main`, `--all`, `--mirror`, `--branches`, wildcard refspecs, a merge commit API call into `main`, and a target behind a shell expansion block from the text alone.
- The `tool_call` hook in `orchestration/pi-extension.js` runs it after the tool profile check, for every `bash` and `powershell` call, nested ones included. Most commands pass the text check, so no session kind or lookup is read. Otherwise the hook reads the session kind (an unreadable kind guards), gathers the named facts with `git symbolic-ref`, `git for-each-ref` and `gh pr view` / `gh api graphql` in the session's directory (10 s deadline, no prompts) and judges again. A failed lookup, an unknown directory (`cd ~`, `--git-dir`) or a push after a git command that can change the branch in the same call blocks: the facts are read before the command runs.
- The reason starts with `Merge guard:`, says what targeted `main` or which lookup failed, and states the policy, so the agent sees why and that `dev` stays allowed.
- It reads command text only, so a script file, an alias or a tool other than `bash` and `powershell` gets past it. It is a soft barrier against mistakes, not a sandbox; the real enforcement is agent credentials without merge rights (#199).
- `merge-guard.test.js` tables the commands and the hook with a fake lookup; `merge-guard.e2e.test.js` runs a faux model through the real daemon against a local bare repository and a stand-in `gh` on `PATH` (POSIX only).

## Deliberate limits

This module defines the authenticated session API boundary consumed by the Pi-native session UI. Session leases coordinate PiChamber daemons only: the standalone `pi` CLI runs its own foreground runtime and does not honor these leases, so concurrently editing the same session through PiChamber and `pi` remains unsupported until Pi provides compatible upstream locking. Resource configuration and richer attachment extraction remain owned by their dedicated workstreams. The session event stream is SSE over the existing authenticated runtime transport; WebSocket callers fall back to it, preserving direct and relay behavior without a second daemon listener. The public route emits named heartbeat events so native `EventSource` clients can detect a silent foreground connection, reconnect, and resume from their last accepted sequence.

The Pi SDK is pinned exactly at `1.1.0`. Any Pi minor or major upgrade requires a deliberate SDK/release-note review and repeat of this module's disposable-runtime smoke validation.

## SDK upgrade validation

The 0.99.2 → 1.0.2 upgrade changes no contract the daemon depends on. The 1.0.0, 1.0.1 and 1.0.2 release notes change the TUI (fullscreen by default), MCP OAuth and project overrides, codemode, `/login`, and add `pi.registerToolRenderer()` and per-thinking-level sampling in `models.json`; none touches the session runtime, prompt preflight, fork and tree, extension UI dialogs, RPC, settings or model catalog APIs the daemon uses, and every SDK export the server imports still exists. The session JSONL format and user data are unchanged, so no migration is required. The SDK package no longer ships `npm-shrinkwrap.json`; `bun.lock` pins its transitive dependencies for PiChamber, with all `@earendil-works/*` packages at 1.0.2. A foreground server on 1.0.2 against a real Pi 1.0.2 agent directory listed and opened existing 0.99.2 sessions, created a session, completed a prompt, and ran the installed extensions with an empty daemon log.

The 1.0.2 → 1.1.0 upgrade changes no API the daemon uses: its release notes add `+name`/`-name` tool selection, OSC 7501 program status, `durationMs` on tool events, `aborted` on `agent_settled`, Claude Haiku 5.5 and codemode and MCP fixes, and every SDK export the server imports still exists. The one change the daemon makes for extensions is `host-extension-runners.js`: the daemon runs the unbundled SDK while the `pi` CLI entry resolves to the bundled one, so extensions that wrap tool execution (pi-fabric) patched a different `ExtensionRunner` class than the one running daemon sessions and every non-read tool failed with "unavailable until extension tool hooks initialize". The daemon now registers its own `ExtensionRunner` in the `Symbol.for('pi-fabric.host-extension-runners.v1')` registry on `globalThis` when `session-daemon.js` loads, which those extensions consult before searching for a runner.

The 0.85.1 → 0.99.2 upgrade changed one contract the daemon depends on: `session.prompt()`'s `preflightResult` callback now receives a disposition (`'started'`, `'queued'`, or `'handled'`) and is called only for an accepted prompt. A rejected prompt throws without calling it. The daemon treats any callback invocation as acceptance and a rejection before the callback as a failed preflight. The remote model catalog request URL also gains `?types=chat,image,classifier`. The session JSONL format and existing user data are unchanged, so no migration or cache deletion is required. Pi 0.99 also ships built-in `mcp`, `codemode`, and `tool-search` extensions, which appear with `builtin:<name>` source names.

The earlier 0.84.1 → 0.85.1 upgrade retained the public session runtime/services API and v3 JSONL format. No PiChamber data migration or cache deletion is required. The SDK repairs a missing trailing newline when opening an existing session; subsequent entries remain separate JSONL records. Existing settings, custom model definitions, labels, and extension entries remain intact.

- `sdk-upgrade.test.js` exercises the installed SDK with disposable directories: cached OpenCode models, user model additions and overrides, forced HTTP refresh, ETag/304, failed refresh preserving the last catalog, restart restoration, and opening/appending a pre-upgrade v3 session.

Same-version, same-path manual dependency replacement is not a release upgrade and requires stopping the old server/daemon before restarting.
