# Pi Session Daemon

## Purpose

This module is the Pi-owned session-daemon foundation. A detached local daemon process creates an `AgentSessionRuntime` with the Pi SDK, tracks it in a registry keyed by Pi session identity and cwd, keeps it behind a private local socket, and maps a small event subset to the PiChamber IPC contract. Browsers never connect to it. Directory inputs must be absolute except for the exact `~` global-session sentinel, which the daemon expands to the server user's home directory before validation. Other relative paths remain invalid.

## Entrypoints

- `../extension-protocol.js` owns the bounded form descriptor and response validation shared by the private daemon bridge and public route projection, so both sides of the IPC seam accept the same field contract.
- Turn ownership: an assistant message belongs to the latest user prompt or displayed custom message (`pi.sendMessage` with `display: true`) before it, live (`assistant.message.start.parentId`, set from the last user start or the `extension.message` id) and in the transcript projection (`parentId` on assistant entries after a `custom_message`). Custom entries (`appendEntry`) and context-only custom messages (`display: false`) never own a turn. `agent_settled` resets the live owner.
- `extension-bridge.js` owns extension UI bindings, pending dialog lifecycle, normalized status/widget/panel/app state, snapshot projection, and extension event publication. `session-daemon.js` supplies runtime lookup, publication, redaction, and directory dependencies through its narrow factory interface.
- `session-daemon.js`
  - `createPiSessionRuntime({ cwd, agentDir })` creates a persistent Pi runtime using the selected server-side cwd and Pi agent directory. It uses Pi's normal settings, credentials, models, sessions, skills, prompts, context discovery, and native extensions. Every runtime creation binds extensions through `session.bindExtensions()` in rpc-like mode with a daemon-owned UI bridge, so pi extensions load exactly as they do under the Pi CLI's RPC mode. Sessions created outside PiChamber (Pi CLI or any other writer of the cwd-scoped JSONL directory) are the same records: `sessions.list`/`open` hydrate from `getEntries()`, then overlay the live `session.messages` / `state.streamingMessage` turn while `isStreaming` is true, including an unpersisted user prompt that has not flushed to JSONL yet. A later prompt must overlay live turns onto that log rather than replace it. An unmatched `toolCall` projects as `running` only while `isStreaming` is authoritative; the same unmatched call in an idle persisted turn projects as a timestamped interruption error instead of malformed `completed` state. `getSession` also reports `isStreaming` and `lifecycle` so a restarted UI can restore the working/tooling state without waiting for the next token.
  - Extension bridging: blocking dialogs (`ctx.ui.select/confirm/input/editor`, plus the PiChamber-specific `ctx.ui.form` which resolves with a values object keyed by field id) publish an `extension.dialog` event and stay pending until answered by the `extensions.respond` private command; every answer, timeout, abort, session close, or daemon stop publishes an authoritative `extension.dialog.dismiss` event before resolving the extension so every connected client removes the modal (timeouts resolve defaults, abort resolves cancellation, form answers travel as a sanitized `values` record and are rejected unless required fields, number bounds, select options, and checkbox values match the pending form); fire-and-forget calls publish `extension.notify`, `extension.status`, `extension.widget`, session-scoped `extension.editor`, and `extension.title`; extension errors publish `extension.error`; appended custom entries and displayed custom messages publish `extension.entry` / `extension.message`. `pichamber.ui` entries with a stable `id` are additionally mirrored into normalized `extension.ui` panel events (latest wins per id, `removed: true` unregisters) and `pichamber.app` entries into sandboxed `extension.app` app surfaces; extension live state is kept in per-session maps and included in both `sessions.open` and `session.snapshot`. The open response must cover every extension event at or below its `lastSequence`, so first attach cannot skip one-time startup statuses before the browser stream connects; reconnect snapshots rebuild the same live panels. TUI-only component replacement, footers, and themes remain intentional no-ops; standard RPC editor replacement and window titles are projected to the focused browser session. Pending dialogs are cancelled when the owning runtime hits idle disposal or daemon stop so no extension thread blocks forever. Unknown dialog responses return `{ resolved: false }` rather than throwing so a stale client retry cannot tear down the shared socket.
  - `createSessionDaemon(options)` starts/stops the authenticated local socket daemon and validates its endpoint and setup inputs. Test seams inject `createRuntime` for resident runtimes and `createServices` (default `createAgentSessionServices`) for transient per-mutation prompt services.
  - Default runtime: calls without a session id (providers, models, settings, and through them the model lookup of every orchestration spawn) run on the default runtime. Every switch of the default records it as the dormant session through `setDefaultRuntime`, so reopening never names an older session. When no default runtime is live, `startRuntime` adopts the dormant session if it is live again, forgets it when its JSONL or working directory is gone (deletion forgets it directly), and starts fresh in the daemon cwd when the requested directory no longer exists. A runtime that won the race for the same session becomes the default and keeps its lease. The losing runtime is disposed, or, when disposal fails, kept with the failed-create cleanups that delete and stop retry. A failed start releases the session lease only while no other runtime of the daemon owns or is opening that session. While a failed-create cleanup for a session is pending, no path (idle disposal, stop, delete) releases its lease; it goes once that cleanup has disposed its runtime (#164, #171).
- `session-replay.js` owns the byte- and count-bounded contiguous replay suffix (`MAX_REPLAY_EVENTS`, `MAX_REPLAY_BYTES`, `createSessionReplayLog`). It caches one serialized line per event for broadcast/replay reuse and reports contiguity (`canReplay`) without trusting filtered delivery.
- `daemon-process.js` is the detached private-process entrypoint. It reads the daemon credential from its owner-only sidecar, starts the socket, writes non-secret identity state only after readiness, persists an accepted ownership claim before acknowledging it over IPC, and removes only its own state on signal shutdown.
- `ipc-client.js` is the server-only authenticated request client. It owns JSONL framing and never exposes endpoint or credential values to callers.
- `runtime-registry.js` owns active runtime identities and session-local subscriptions. It rebinds the subscription after an SDK session replacement, rejects identity conflicts rather than displacing another runtime, and attempts every tracked disposal even when another disposal fails.
- `session-jsonl.js` validates cwd-scoped Pi JSONL before discovery. Create, rename and daemon startup require a valid session header per file (`validatePiSessionJsonlDirectory`); they do not read whole transcripts. `sessions.list` uses `listPiSessionJsonlDirectory` (header, first user prompt from a bounded 512 KiB head, latest rename). The listed name follows Pi's `SessionManager.getSessionName`: the latest `session_info` entry anywhere in the file, where an empty name clears it. A fork copies its parent's path including the parent's title, so a later rename can lie megabytes before the end; a fixed-size tail would miss it and list the parent title again after a restart or idle unload. Without a memo the reader therefore scans backwards from the end in raw byte chunks (`session-info-scan.js`, only lines containing the `"session_info"` marker are parsed) until the first rename or the end of the head scan; a large session that was never renamed is read once in full. The daemon passes one `createPiSessionListCache()` memo per process: a file whose inode, size and mtime are unchanged is not read again, a file that grew is searched only after the last complete line already scanned, after checking that it still starts with the remembered header line and that offset is still a line boundary. A shrunk, replaced or otherwise rewritten file, a trailing line that is still being written, and a file whose first prompt is not known yet fall back to the full read. Files in one directory are listed with at most eight concurrent reads. One file does not fail the listing of the others (#126): a file removed since the directory was read is absent, and any other failure (malformed header, unreadable file) skips it, logs only its error code (no path, no content) and marks the returned array `incomplete: true`. An unchanged malformed file stays in the memo and is neither read nor logged again until it changes. Lookups that list a directory (`findPersistedSession`, `orchestration/session-lookup.js`) treat an `incomplete` listing without a match as a failed lookup, not as absence. When that failed lookup located the session's own file (a filename match with an unreadable header, a listed file whose body fails validation, or a header scan hit that fails validation), `findPersistedSession` answers that file's `MALFORMED_SESSION_JSONL` or `SESSION_JSONL_UNREADABLE` instead of `INVALID_SESSION` (#191), so open and delete report "found but unreadable"; A lookup that failed otherwise (an unreadable session directory, an `incomplete` listing) also answers `SESSION_JSONL_UNREADABLE`, because it proves no absence and the client reads `INVALID_SESSION` as a deletion. `INVALID_SESSION` is only for a complete miss. Orchestration treats these codes as a retryable caller lookup, not as a gone caller. `POST /api/pi/sessions/:id/archive` applies the same rule: an id missing from an `incomplete` list answers `SESSION_JSONL_UNREADABLE` (503), a complete list without it answers `INVALID_SESSION` (404). `sessions.list` passes the marker on as `incomplete: true` next to `sessions` (absent for a complete listing), and `GET /api/pi/sessions` forwards it to the client. Only a failure to read the directory itself fails the listing. Full-file validation remains on open of a specific session so a malformed body still fails that chat. Pi's SDK list is not the production list path because it scans every line of every log. Directory names match Pi's SessionManager encoding, including Windows drive letters and Git Bash/MSYS/Cygwin/WSL `/c/...` paths so PiChamber and the Pi CLI share the same JSONL sessions.
- `supervisor.js` resolves server-only overrides, creates the credential, serializes start/reuse/stop through an owner-only lock, validates daemon identity through `runtime.health`, forwards server-owned commands only after that identity check, and starts or stops the detached process. Reuse requires the ready-state sidecar `entrypoint` to match this checkout's `daemon-process.js`; a healthy same-profile daemon with a different entrypoint is claimed and then shut down through authenticated IPC so local `bun run dev` cannot keep answering `getSession` without the live-turn overlay. When the parent is Electron, the child is spawned with `ELECTRON_RUN_AS_NODE=1` so packaged Windows/macOS/Linux apps run the daemon as Node instead of a hidden second Electron GUI process.
- `../server/server-profile.js` derives one stable daemon profile per server: installed web is `web-p<port>`, development web is `web-dev-p<port>`, installed desktop is `desktop`, and development desktop is `desktop-dev`. `PICHAMBER_SERVER_PROFILE` overrides the derivation with a hashed `custom-<hash>` key so raw input never becomes a path, while preserving whether the launcher is a development build for stale-code replacement. The profile key is stable across restarts; the server instance id is a fresh UUID per launch. Development launchers (`scripts/dev-web-hmr.mjs`, `scripts/dev-web-full.mjs`, `cross-env` in the `dev:server` scripts, `PICHAMBER_ELECTRON_DEV`) explicitly mark themselves so stopping development can never terminate the installed daemon.
- `../server/cross-process-lock.js` serializes critical sections across servers sharing one data directory (exclusive create, owner nonce, dead-pid steal, bounded wait). It backs the daemon operation lock pattern and every shared read-modify-write store below.
- `session-lease.js` owns exclusive cross-daemon residency of one Pi session, keyed by canonical agent directory, cwd, and session id under `<agentDir>/.pichamber/locks/sessions/`. The lease is acquired before a resident `AgentSessionRuntime` is created and released after idle disposal, deletion, replacement, or daemon shutdown. Opening or deleting a session leased by another live daemon returns `SESSION_IN_USE` (HTTP 409) while the session stays visible in listings; opening one whose stored working directory was removed returns `SESSION_DIRECTORY_MISSING` once the lease shows no other daemon holds it, and aborting it then has nothing to abort and succeeds (#177); different sessions remain fully concurrent. Lease files from different `PICHAMBER_DATA_DIR` values still coordinate because they live under the shared agent directory.
- `../routes.js` registers authenticated public adapters before the generic proxy. It exposes only whitelisted runtime, project, session, provider-auth/configuration, settings, resource, small-model utility, and SSE event shapes; no browser response contains daemon paths, credentials, PIDs, headers, or socket framing. Session actions are path-selected, so an identity supplied in a request body cannot redirect a mutation. `POST /api/pi/sessions` projects the created detail through the same session-detail projector as `GET /api/pi/sessions/:id`, so extension items appended from `session_start`, the `streamEpoch` stamp, and extension UI snapshot state are returned rather than rejected; only a malformed detail is `DAEMON_PROTOCOL_MISMATCH`. `archive-store.js` persists PiChamber-only opaque session archive metadata atomically beneath the PiChamber data root and never edits Pi JSONL. `settings-store.js` keeps PiChamber new-session defaults separate from Pi settings.json. `/api/pi/small-model/generate` reads that sidecar and runs a bounded in-memory no-tools Pi session, so utility generation creates no visible or persisted session and exposes no model or credential details. `GET /api/pi/settings` copies leftover UI/desktop `defaultModel` / small / walkthrough strings into that sidecar when those sidecar fields are unset, then Sessions settings is the only editor. Sidecar `defaultThinkingByModel` is the per-model thinking map (`provider/model` keys). A stored global `defaultThinking` with a default model is copied onto that map key and dropped; global thinking without a default model remains a clamp-only fallback. `ui-settings-store.js` owns portable PiChamber preferences at data-root `settings.json` and host, device, and secret-bearing values at `runtime-state.json`. `/api/pi/ui-settings` merges both views for existing clients and splits writes through explicit field allowlists. It migrates an unscoped flat file once; after the portable scope marker exists, local fields found in `settings.json` are ignored rather than applied to the host. The route is not available through removed `/api/config/*` aliases. `session-folders-store.js` validates and atomically persists the restored sidebar's folder snapshot at `/api/pi/session-folders`; a missing snapshot is distinct from an empty one. `custom-themes.js` serves validated custom-theme candidates from `/api/pi/themes` with per-file partial-failure isolation. `model-config-store.js` atomically updates Pi's credential-blind `models.json`; literal keys continue through Pi auth and headers are write-only. `providers.config.get` returns `config: null` for a provider that is not in `models.json` (built-in catalog entries) and fails only when that file is present but malformed.
- `../event-stream.js` owns the `/api/pi/events` SSE connection lifecycle so `../routes.js` stays a thin adapter. Per connection it installs cleanup before `subscribe` is awaited (a client that leaves during the opening window cannot leak a daemon subscription; a late subscription is closed exactly once), funnels client disconnect, subscription error, and server shutdown through one idempotent cleanup, hands an `AbortSignal` through the supervisor to the private IPC subscriber, never writes a named heartbeat or a late frame to a dead response, and byte-bounds the response socket buffer (`res.writableLength`, default 8 MiB, aligned with the daemon replay budget) with the bound enforced BEFORE each write so no single frame overshoots it. A client that stops reading is disconnected recoverably — the stream ends and the client reconnects from its last accepted sequence for replay or an authoritative snapshot, so no event is silently removed from an otherwise contiguous stream, but frames still buffered when the disconnect fires are not promised as delivered; the reconnect replay is the delivery guarantee — while a healthy client's connection stays independent of the slow one. Every teardown is bounded: a `write()` that returns false starts a drain deadline (default 5s) that ends even a quiet never-draining client, and after `res.end()` a terminate deadline (default 5s) destroys the response, because `end()` alone only queues the FIN behind unflushed data and would otherwise leave a stalled socket open forever and hang server shutdown/close. The response `'error'` guard stays attached for the response's lifetime (idempotent; cleanup can complete while data is still in flight and a late unhandled `'error'` would crash the process). The registry tracks live connections so `registerPiRuntimeRoutes` can expose `closeEventStreams()` for server shutdown, ending active and still-opening streams (and their daemon subscriptions) before the HTTP server closes. The IPC subscriber removes its abort listener and destroys the opening or active daemon socket on cancellation.
- `orchestration/` owns session orchestration (#107, [ADR 0010](../../../../../../docs/adr/0010-orchestration-through-daemon-tools.md)). `session_list` and `session_read` report each session's state, the outcome and error of its last turn and, while it runs, an `activity` object (run duration, time since the transcript last changed, automatic retry with the provider error, a blocking dialog), so an orchestrator can spot a stuck worker without polling transcripts. `tool-contracts.js` defines the tools (`orchestration_capabilities`, `orchestration_digest`, `orchestration_takeover`, `session_spawn/list/read/send/wait/interrupt/stop/rewind`, `worker_report`) and their schemas; `worker_report` is for workers only (`orchestratorAllowed: false`, hidden from orchestrators' active tools), `orchestration_digest` for orchestrators only. Worker reports (#117): `worker_report` (`progress`, `question`, `blocked`, `ready`, `done`) is validated per kind and stored on the worker in one registry `update` (`recordReport`); a retry with the stored `clientRequestId` changes nothing. A `question` or `blocked` stays open as `worker.question` until a report or a `session_send` from the owner names its id in `resolves` (closed only after the send was accepted); one is open at a time, and a new one must name the open one, which it replaces. Every admitted input sets `worker.lastInputAt` and leaves the question open. A `done` report binds to its own run in the same `update` (`doneReported`), so the worker becomes `done` and frees its slot only when that run ends; without a run of this service it is only stored. A reported pull request is kept as `{ number, repository }` from the worktree's `origin`. Every run end stores `worker.snapshot` (`lastProgressAt`, the last turn's `lastError`, Pi's `getSessionStats` totals as `usage`, each with its time), so `orchestration_digest` reads the registry and the live channels only, never activates a session, shows `live: 'dormant'` without a resident runtime and `null` for anything unknown. Ownership and bookkeeping live in one durable registry, `<dataDir>/pi/orchestration-registry.json` (#118): `registry-store.js` replaces it atomically under the per-file lock and serialises every change through `update`, and fails on a malformed file instead of reading it as empty; `worker-registry.js` holds the pure document changes. A spawn is a journalled operation (`reserved`, `session`, `prompted`, `durable`) whose slot is reserved in the same `update` as the daemon-wide limit check and held until the proven end of the worker's last run. The same `update` claims the canonical directory (`canonicalDirectory`, realpath): one starting or active worker per directory across all daemons of the data root, also for a prompt to a finished worker (`ORCHESTRATION_CWD_BUSY`). The host gate (#119) runs in that same `update`, after the limit check and only for a new spawn, never a resume: with `orchestration.gate.enabled` (default on) it refuses with `ORCHESTRATION_HOST_BUSY` and the numbers in the reason while the 1 minute load is above the core count or fewer than `orchestration.gate.minAvailableBytes` (default 8 GiB) are available. `host-info.js` reads the numbers (`hostGateNumbers`, `os.freemem()` is MemAvailable on Linux); `orchestration_digest` returns the same `host` numbers with the worker count and limit. The worker's lineage entry carries the `opId`, so a crash at any step resumes or releases it: `session-lookup.js` finds the session through the resident runtimes and then the persisted sessions of the start's directory, with the read failure rule of `scanPiSessionJsonlHeaders` (a file removed after the listing is absent, any other read failure leaves the scan incomplete and it goes on with the other files; unlike that header scan, an unparseable entry is no proof either, since the lineage entry may sit behind it), a failed lookup, or a session file whose entries before the first message cannot be parsed, keeps the start undecided (`SESSION_LOOKUP_FAILED`), a worker whose JSONL never reached disk goes back to `reserved` with its slot and is recorded as `replaced`, so neither lookup adopts it again or lets it hide the recreated session, and a prompt step is not sent again when the transcript holds a user message with exactly the task's text (a transcript that cannot be read now leaves the start open with `ORCHESTRATION_START_UNDECIDED`). Every transitional record names its daemon process (`process-identity.js`: pid, kernel start time, instance), so a reused pid counts as dead; the dead-process check runs before every call, rechecks the stamp in the writing `update`, and finishes only records of dead processes. A stop whose process died keeps the worker and its slot until `session_stop` is retried. Every input (UI prompt and `session_send`) passes one admission contract (#125 round 5). `beforeSessionInput` only fails fast before the daemon activates a session and decides nothing. With the session resident and its lease held, right before `prompt()`, the daemon calls `admitInput`: one registry `update` checks a running stop, the limit and the directory and, for a `done` or `stopped` worker, takes its slot and directory as `admission` (`{ token, process, previous, since, state }`); another admission of the same process shares it, and one of another live process refuses with `ORCHESTRATION_WORKER_BUSY`. The ticket ends only with Pi's verdict on that prompt (`resolveInput`), never with a check made before the call, because Pi 1.1.0 runs input handlers between the call and its own streaming check (CONTEXT.md): `started` passes the slot to the run as a new `generation` (`commitStart`), counted once; `queued`, `handled` and a rejection end the ticket without a run, and once no ticket of the worker is open the admission's slot goes back and a settle that waited for the tickets applies. A settle applies the `done` rule only to its own generation, so a late settle of an earlier run changes nothing, and it waits while an admitted ticket has no verdict, since that input may start the next run. A prompt Pi accepts without a verdict (deferred while `agent_settled` handlers run) is `unresolved`: nothing is rolled back, the slot stays and the registry shows `admission.state: 'unresolved'` with `unresolvedAt` until its late verdict (Pi runs the deferred prompt again) or a stop; a watchdog (Slice 4) reports one that stays. Every registry step of a ticket names its admission token and applies only while the worker still shows that admission (#125 round 6): a run that `started` holds the admission's slot from its verdict until its own settle, so neither a settle of the run before it nor the end of a sibling ticket frees it, and when its `commitStart` fails nothing is rolled back: the run's next registry step (its done report or its settle) completes the commit as `completeStart`, so the report binds to the run's own generation and an earlier run's `done` never ends it (#125 round 7). A settle never sets `done` while the worker shows an admission. A stop ends the admission and makes every remaining ticket stale; a late `started` of a stale ticket confirms nothing, also not a newer admission, and aborts only its own run: the daemon binds each `started` verdict to the run Pi starts for it (`run-binding.js`, the agent's `AbortSignal` that is new one microtask after the verdict) and aborts it only while that signal is still the session's run, in one synchronous step. SDK assumption (Pi 1.1.0, `CONTEXT.md`): Pi starts the run in the same synchronous step that reports `started`; `run-binding.e2e.test.js` pins it. A verdict without its own run (another run took the agent first) aborts nothing. Each `started` verdict has its own start identity (the ticket token, with the order of the verdicts), fixed before the first await; several inputs may share one admission, so the admission is a grant of the slot and not the identity of a run (#125 round 8). `completeStart` returns a generation only for the same start and never hands an older start the generation of a later one; a done report and a settle freeze their run's start before the first await and apply only to it, with no fallback to the current generation, and a done report without a live run of this service records nothing. An `agent_settled` event is only a candidate: while the agent still has a `signal`, also an aborted one, a run is live, so the daemon drops the event before it publishes idle, ends a pending input or wakes the owner (`isSettleFinal` in `run-binding.js`). A bound signal permits an abort but proves no completion; an aborted run is not over until it settled, and a retry, `agent_before_settle` or a continuation makes a new signal without a new `started`. No settle, with or without a signal, ends a run's occupancy: only the end of the `prompt()` call that reported its `started` verdict does (`provenRunEnd` in `run-binding.js`; Pi 1.1.0 resolves it after the run, every retry and continuation and its `agent_settled` handlers, CONTEXT.md). The settle only stores the run's result, applied with that proof. A `started` verdict that bound no run of its own keeps its admission until its prompt ended. A late verdict (Pi ran a deferred prompt again) has no prompt of its own, so its run, aborted or not, holds the slot and directory as `hold` (`reason: 'unproven_run'`), reported as `ORCHESTRATION_RUN_UNPROVEN`, until the holding process is dead. A stale run that cannot be bound is not aborted (it may be another valid run). Every occupancy (`starting`/`active`, an admission, a hold) counts in the limit and in the directory check. Limit of this contract: Pi 1.1.0 gives no unique run identity and can emit `agent_settled` while another prompt's run is live. PiChamber frees a slot and directory only on a completion it can attribute; missing or contradicting evidence keeps the occupancy, which can lower capacity for good. Other workers stay protected; an unbound stale prompt is no reason to abort their run. No signal is not proof of completion either (a run waiting in its retry backoff has none), so an attributed completion stays an SDK assumption pinned by `run-binding.e2e.test.js`. Detecting and reporting such held claims belongs to Slice 4; neither another settle nor a timeout confirms their end. A registry write that fails while recording a start likewise rolls nothing back (a held slot is better than a rolled back worker) and is published as `session.error` `ORCHESTRATION_ADMISSION_UNRESOLVED`. The reconcile releases the admission and the hold of a dead process; its runs ended with it. A session without lineage passes even when the registry is unreadable; workers and tool calls then fail. `contract-validator.js` checks every argument against the published schema (`INVALID_ARGUMENT`), and a caller whose session no longer exists gets `ORCHESTRATION_CALLER_GONE`; a lookup that failed on storage errors is not proof of absence (`findPersistedSession` marks it `incomplete`; only a missing sessions root, store or file counts as absent, a store that vanished mid-scan is skipped, not the end of the scan, and a same-id file that does not validate only marks the lookup incomplete while the scan goes on to a later valid one) and fails with the retryable `SESSION_LOOKUP_FAILED`, so no credential is revoked for it. The caller of `orchestration.call`/`caller` and every session a tool uses (read, send, wait, abort, the old owner a takeover checks, a resumed start's worker during its prompt step, a parent whose legacy workers are imported, and the owner a wake is sent to, until Pi accepted it) hold the idle guard (`holdSession`) like direct requests for the whole use and are disposed again when idle. The guard only keeps a disposal from starting, so a runtime whose idle disposal already runs is not live for orchestration (`getLiveRuntime`): its users wait for the disposal in `activateSession` and reopen the session, and a wake is never sent into a runtime that is being torn down (#190). A spawn retry while the first task is still being accepted shares that outcome, and each send holds its own pending token, so a receipt retry never ends a newer send's run. A worker whose first task Pi rejects is stopped with `task_rejected` and frees its slot. `policy.js` decides every call: workers get only `childAllowed` tools, `session_stop`, `session_rewind` and `worker_cleanup` need ownership, `session_send/read/interrupt` reach any session. `session_rewind` (#116) moves an idle worker of the caller to an earlier entry of its active branch through the daemon's `navigateSession` (the function behind `sessions.navigate`: alias resolution, Pi's `navigateTree`), optionally prompting it in the same call; it refuses `ORCHESTRATION_SESSION_BUSY` while the worker runs, retries, starts, waits for input or has a direct input Pi has accepted but not yet turned into a run (`activity.inputActive`, from `activeSessionInputs`), and `SESSION_TREE_NOT_FOUND` for an unknown entry. A repeated `clientRequestId` replays the first answer (`deduplicated`) without navigating again (per process, like the send receipts), and a different entry or prompt under it is `OPERATION_PAYLOAD_MISMATCH`. It undoes no file change or command. `session_read` lists the messages of the active branch with their `entryId`. `orchestration_takeover` moves all workers, open operations and retry keys of an idle orchestrator to the caller in one `update`; it refuses with `ORCHESTRATION_TAKEOVER_BUSY` while the old orchestrator runs, is resident in another daemon, a start step of it runs in a live process, or a stop of it is still aborting a worker (importing an old orchestrator's JSONL child entries once), and a late step write or stop claim of the old owner fails with `ORCHESTRATION_OWNER_CHANGED`; a stop claim carries its own token, so only that stop finishes, releases or reports it (a stop that lost its claim fails with `ORCHESTRATION_STOP_CLAIM_LOST`). A second stop of a worker shares the stop running in the same service, and a live claim of another process is never replaced (`ORCHESTRATION_STOP_BUSY`). A stop waits for the verdicts of inputs admitted before its claim and aborts the run they started. When Pi accepted an input that has no verdict yet, the stop ends the worker but keeps its slot and directory as `hold` (`reason: 'unresolved_input'`) and names it in `held`, since neither a local abort nor a stale ticket proves that Pi will not run it; the hold ends with that input's verdict (`queued`, `handled`, a rejection) or with the proven end of the run it started. A run whose verdict arrives after the worker stopped is aborted at once and holds the slot (`stale_run`) until its prompt proved its end; without that proof the hold stays (`unproven_run`). Inputs arriving behind the claim fail with `ORCHESTRATION_WORKER_STOPPING`. `orchestration-service.js` handles the tools, idempotent spawn by `clientRequestId` through `requestKeys`, stop (abort first; a failed abort keeps the worker and its slot and fails with `ORCHESTRATION_STOP_FAILED` naming the stopped and failed ids, a session that no longer exists counts as stopped, and so does one whose working directory was removed: its abort is a no-op, #177). Wakes (#117, `wakes.js`, in memory) replaced #107's result delivery: a worker's run end (`run_finished`, or `run_failed` with the provider's error line when the run ended in an error after Pi's retries, or `done` when it ends the run a `done` report bound to), a `question` or `blocked` report addressed to the orchestrator (`question`, `blocked`; a report with `audience: owner` queues nothing), a `ready` report (`ready`) or an extension dialog opened in it (`question`), and a busy worker without an open dialog and without message, tool or report activity for `watchdog.stallAfterMs` (`stalled`, once per episode, checked on a 15 s tick between the daemon's `start` and `stop`) queue one event `{ sessionId, kind, reason, at }` with a one line reason of at most 200 characters. Routing (#156): the last writer decides. Every input is admitted with its source, `owner` (UI prompt, the default) or `orchestrator` (`session_send` through the service's `sendInput`), and `resolveInput` records it per worker as `lastWriter` when Pi's verdict says a run started or may start; a plain run end (`run_finished`) is queued only when the orchestrator was the last writer, while `run_failed` and `done` always are. The per-worker switch "Orchestrator: follows / quiet" is the worker's id in `orchestration.quietWorkers` of the settings sidecar (`{ <id>: true | null }` through `PUT /api/pi/settings/defaults`, resolved as `quietWorkers: string[]`, read at every flush); for a quiet worker `wakes.js` drops, when a batch is sent, every event except `done`, `blocked`, `ready`, `ci_passed`, `ci_failed`, `pr_merged` and `pr_closed`. The rule sits in the daemon, the UI only sets the id; `orchestration_digest` and `session_list` read the registry and ignore both rules. The owner is read from the registry when a batch is sent, so a takeover delivers to the new owner, and events of a stopped or unknown worker are dropped. An idle owner gets the batch `wakes.coalesceMs` after its first event, a busy one at its next settle; only the owner's own settle sends before the window ends, a worker's settle and the watchdog tick wait for it. The batch goes out as one `pichamber.orchestration.events` custom message (one line per event plus a pointer to `orchestration_digest`, `triggerTurn`, `followUp`); entries leave the queue only after the send resolved, so events emitted during a send go out in the next message. A dormant owner is reopened like any session a tool uses; `SESSION_IN_USE` or a failed send keeps the queue for the next tick, and a deleted owner drops it. Queued events are not persisted; the instructions tell the orchestrator to read the digest after a restart or compaction. `RESULT_MESSAGE` stays exported so old transcripts still render. `pi-extension.js` is Adapter A: an inline, hidden extension loaded into every runtime that registers the tools as `mcp__pichamber__<tool>` and appends `instructions.js` (adapted from t3code, MIT, T3 Tools Inc.) to the system prompt of every turn of a session marked as orchestrator, through `before_agent_start` (#136). The mark is the session id in `orchestration.orchestrators` of the settings sidecar (set in the file or with the session row menu's one switch through `PUT /api/pi/settings/defaults`, `{ orchestrators: { <id>: true | null } }`), read on every call and every turn, so it survives restarts and acts on the next turn. `sessionKind` decides `worker` (lineage, even if marked), `orchestrator` (marked) or `unmarked`: workers get only their tools, unmarked sessions neither tools nor instructions, and `policy.js` refuses every call of an unmarked session with `ORCHESTRATION_FORBIDDEN`. Pull request watch (#119, `pr-watch.js`, in memory): while a live worker has a reported `pullRequest`, the web server's `lib/pi/pr-watch-poller.js` asks the private `orchestration.prWatch` command for the targets every 60 s, reads each pull request through the GitHub module (`readPullWatch`, github.com only) and hands the reads back as `{ reads }`. `diffPullRequest` compares a read with the last one and queues the wakes `ci_passed`/`ci_failed` (final combined check result, once per head commit), `review_activity` (more issue plus review comments) and `pr_merged`/`pr_closed` (once); a stale, partial or failed read changes nothing. After a daemon restart the first read reports an already final CI result or a merge once and only seeds the comment count. `orchestration.github.enabled` (default on) turns the watch off: no targets, no GitHub call. `worker_cleanup` (#118, orchestrator only, ownership required) removes a worker after the owner merged its pull request: the orchestrator calls it on `pr_merged`; nothing removes a worker on its own. `cleanup-guard.js` is the pure rule: a fresh, uncached `findPullForBranch` read (`lib/github/merge-lookup.js`, run in the daemon) must show a merged pull request for exactly the worker's head branch with its head equal to the local tip, the worktree must be clean; `main` and `dev` never qualify, and a failed lookup, an open or closed unmerged pull request, later local commits or a dirty tree refuse with a reason and remove nothing. Only a linked worktree qualifies, never a main checkout. The call holds the worker's `stopping` claim from the first check to the end (new inputs get `ORCHESTRATION_WORKER_STOPPING`, the claim is released on a refusal or failure) and the session's idle guard; as for takeover, only a session proven idle in this daemon passes, so one resident in another daemon, one that cannot be activated here, a run, retry, dialog, direct input, admission, open input or a `hold` a stop left for an unsettled input or run refuses. Run and tree are read again after the GitHub read, right before the first git step. A worktree still present must hold exactly the stored branch at the merged head; a retry that finds a detached or other branch there refuses, only a missing worktree counts as removed. `worker-cleanup.js` then runs `git worktree remove` (never `--force`), `git branch -D` (squash merges leave the branch unmerged in git's eyes) and `git push origin --delete --force-with-lease=refs/heads/<branch>:<merged head>` when the remote branch still exists; the daemon's `deleteSession` deletes the session and the registry forgets the worker. The target (worktree, git dir, branch, repository) is stored on the worker before the first step, and each step checks what is left, so a call after a failure (`WORKER_CLEANUP_FAILED` with `step` and `removed`) continues. ## Protocol and security invariants

- Each profile owns its daemon artifacts: `<dataDir>/pi/daemons/<profileKey>/` holds the credential, `daemon-state.json`, and `operation.lock`; the endpoint is `<runtimeDir>/pi-daemons/<profileKey>/daemon.sock` (or `$XDG_RUNTIME_DIR` equivalent); per-profile logs append to `<dataDir>/logs/pi-daemon-<profileKey>.log`. The state sidecar records `profileKey`, `serverInstanceId`, `serverPid`, `daemonId`, `runtime`, and `buildId` alongside pid, endpoint, and entrypoint. A pre-profile legacy daemon is never adopted, unlinked, or signaled; only its dead pid record is best-effort removed.
